## Goal

Portar as 5 camadas de arestas SVG com pan/zoom do app client para `@shopify/react-native-skia` (eliminando o crash OOM no Android), mantendo o export SVG integral e adicionando PNG como segundo formato de export, configurável em Settings.

## Success Criteria

- Todas as telas de canvas (board, location map, story/choices, relations, location graph) abrem no Android sem crash, com qualquer conteúdo e em qualquer zoom.
- Arestas nítidas durante e após o pinch (sem blur de bitmap esticado entre re-syncs).
- Paridade visual no web (`expo export`) e no desktop (Electron) com o comportamento atual.
- Export SVG inalterado nos 10 pontos de export (arquivos equivalentes aos atuais).
- Export PNG do documento inteiro funcionando nos mesmos pontos, no Android e no web.
- Setting "export format" (`svg`/`png`) persistido e respeitado por todos os exports.
- Suite do client, typecheck e lint verdes.

## Perguntas do solicitante — respostas

1. **Licença da lib nova? Compatível com a MPL-2.0?** Sim. O pacote `@shopify/react-native-skia` é **MIT** (Shopify) e o motor Skia embarcado é **BSD-3-Clause** (Google) — ambas permissivas. Usar código MIT/BSD a partir de um projeto MPL-2.0 é compatível na leitura padrão: a MPL-2.0 é copyleft fraco por arquivo e não "contamina" a dependência; a única obrigação é preservar os avisos de copyright (Fase 1 inclui um passo de atribuição). Fontes em `Sources`.
2. **SVG export continua funcionando? Exporta o SVG como um todo?** Sim, e já é "como um todo" hoje: os builders `*Svg.ts` geram strings SVG standalone do **documento inteiro** (não da viewport) e não dependem de `react-native-svg`. O port não toca neles.
3. **Segunda opção PNG nas telas de Settings?** Sim — o plano inclui o setting `exportFormat` (`svg`/`png`) em `AppSettingsScreen` mais o pipeline PNG.
4. **A nova lib simplifica a geração do SVG?** Não a substitui — e esse é o desenho recomendado: PNG reaproveita a **mesma string** dos builders (rasterizada pelo Skia), então não existe segunda implementação de desenho. Pode ser necessária uma auditoria pequena nos builders (ver Fase 3b) para raster fiel no Android.

## Context And Current Facts

- 5 canvas montam `<Svg>` dimensionado em unidades de mundo (`renderWindow`), o que no Android aloca um bitmap ARGB da view inteira e causa OOM ao abrir a tela: `BoardCanvas.tsx` (BoardCanvasScreen), `LocationMapConnectionLayer.tsx` (LocationMapScreen), `StoryGraphCanvas.tsx` (ChoiceViewScreen = gráfico de choices, + ThemePreview), `CharacterRelationGraphCanvas.tsx`, `LocationGraphCanvas.tsx`. Todos usam o hook único `useCanvasViewport`.
- Fora de risco e fora do port: timeline e matrizes (desenham com `CanvasLine`, Views puras), stats radar/ladder (`<Svg>` estático de 300–420dp), `*Svg.ts` de export (strings, não renderização), desktop (web embrulhado), site e admin (sem grafos).
- Export atual: 10 pontos chamam `deliverSvgMap` em `utils/storyTransfer.ts` (presence matrix, location map, timeline, board, relations, location graph, choices, plot matrix, plot coverage, stats). O pipe `deliverFile` já aceita `Uint8Array` + MIME arbitrário e já trata download binário no web — PNG reutiliza o mesmo pipe com `image/png` e extensão `.png`.
- Settings: estado em `state/userSettingsStore.ts` (zustand) persistido na tabela `client_settings` (`db/schemas/clientSettings.ts`) via `ClientSettingsService`; tela em `screens/enterstack/AppSettingsScreen.tsx`, que já tem `SingleSelectPill` (ideal para `svg`/`png`). Migrações de runtime são TS em `src/db/migrations/` aplicadas por `src/db/migrate.ts`; `drizzle-kit generate` (`db:generate`) gera o SQL em `drizzle/`. A unidade de trabalho segue o caminho usado pela última coluna adicionada (verificar nos arquivos da migração mais recente).
- Stack instalado: `expo ~54.0.32`, `react-native 0.81.5`, `react-native-reanimated ~4.1.1`, `newArchEnabled: true` — satisfaz os peers do Skia 2.2.12 (`react >= 19`, `react-native >= 0.78`, `react-native-reanimated >= 3.19.1`).
- Os testes adicionados em `c31d4cfa` (`BoardCanvasEdges`, `LocationMapConnectionLayer`, `useCanvasViewport`) afirmam o comportamento SVG atual e serão invalidados pelo port — a Fase 4 os reescreve e anota o impacto em `docs/TESTING_ROADMAP.md`.

## Constraints And Non-goals

- Sem prazo e sem pressão de release: rollout sequencial por canvas, cada fase validada no device antes da próxima. Sem feature flag de runtime.
- Non-goals: formato JPEG; modo PNG-de-viewport; portar stats, timeline ou matrizes; remover a dependência `react-native-svg` (stats continuam usando); renderizar nós no Skia (nós ficam Views nativas); reescrever a câmera para shared-values/UI-thread (follow-up futuro explícito); mudar a semântica dos builders SVG.

## Key Decisions

- **D1 — Biblioteca e versão.** `@shopify/react-native-skia`, instalado **somente** via `npx expo install @shopify/react-native-skia` para que o Expo resolva o build compatível com o SDK 54; a versão resolvida é registrada e confrontada com `node_modules/expo/bundledNativeModules.json` na Fase 0 (esperado 2.2.x; o registro confirma 2.2.12 com peers satisfeitos pelo projeto). Rejeitado: instalar versão avulsa (risco de mismatch do módulo nativo) e alternativas genéricas (canvas via WebView = lento; módulo nativo próprio = reinventar o Skia pior).
- **D2 — Builders SVG ficam.** Geração de SVG não é reescrita nem simplificada; continua sendo a fonte única do export vetorial do documento inteiro.
- **D3 — PNG = mesma string, rasterizada.** Uma única fonte de verdade para os dois formatos: a string do builder vai para o arquivo (SVG) ou para o Skia (`Skia.SVG.MakeFromString` → `ImageSVG` num canvas do tamanho do documento → `makeImageSnapshot` → `encodeToBytes`) e sai como PNG. Rejeitado: segunda implementação de desenho só para PNG, e snapshot de viewport como PNG principal (viewport vira fallback degradado, ver Riscos).
- **D4 — Resolução do PNG com teto.** Lado maior limitado a 4096px por padrão (conservador frente a limites de textura de GPU); o spike confirma no device de teste.
- **D5 — Setting `exportFormat` (`svg`/`png`), default `svg`.** Nova coluna + store + linha em AppSettings + i18n en/pt; os 10 pontos de export leem o setting. JPEG rejeitado: artefatos em line-art/texto sem benefício (fotos de location maps já vão embutidas nos dois formatos). Suposição reversível: o enum aceita `jpeg` depois sem redesenho.
- **D6 — Nós ficam Views; câmera fica no `useCanvasViewport`.** O port troca só a camada de arestas; layouts em `packages/shared` não mudam (o componente Skia aceita string em notação de path SVG direto, então os `d` atuais passam intactos; culling contra `renderWindow` continua igual).
- **D7 — Uma camada compartilhada, como overlay irmão.** Um componente `SkiaEdgeCanvas` em `features/graphs/` usado pelos 5 canvas, em vez de 5 ports independentes — a divergência ×5 é o que permitiu este bug nascer 5 vezes. Refinamento de implementação (Fase 1): o `<Canvas>` Skia é um **irmão** do plano animado (absolute-fill do frame externo, `pointerEvents="none"`, pintado **antes** do plano para preservar a ordem atual arestas-embaixo/nós-em-cima), NUNCA filho do plano escalado — um canvas filho precisaria de layout em unidades de mundo para cobrir a janela visível, recriando o bitmap gigante (agora na GPU). Consequência: a matriz da câmera no `Group` vem de **shared values Reanimated espelhados pelo hook** (sem commits React durante gestos, sem dessincronia com os nós); o `renderWindow` continua governando só o culling com histerese. `GraphCanvasFrame` ganha um slot `overlay?` renderizado antes do plano interno.
- **D8 — Licença.** MIT (pacote) + BSD-3 (Skia) sob projeto MPL-2.0: compatível; Fase 1 adiciona os avisos de copyright onde o projeto já documenta atribuições de terceiros.
- **D9 — `react-native-svg` permanece** como dependência (stats estáticos, seguros, sem benefício em portar).
- **D10 — Publicação sequencial por canvas**, sem flag: cada canvas portado é uma unidade revisável e reversível por revert.

## Recommended Approach

Trocar, em cada um dos 5 canvas, o `<Svg>` world-sized pelo `SkiaEdgeCanvas` compartilhado: um `<Canvas>` Skia absolute-fill do frame (irmão do plano animado, fora do transform, `pointerEvents="none"`, pintado antes dos nós) contendo um `<Group>` com a câmera vinda de shared values espelhados pelo hook, os mesmos paths (strings `d` reaproveitadas) e labels em texto Skia com fontes via `useFonts`. A câmera continua calculada por `useCanvasViewport`; o overlay/`renderWindow` continua governando só o culling. Nós, timeline, matrizes, stats, builders e delivery não mudam de forma — PNG entra como segundo formato do mesmo pipe.

## Work Plan

- **Fase 0 — Spike (time-box, 1–2 dias).** Instalar via wrapper Expo; canvas hello-world no Android e no web; registrar versão resolvida + confronto com `bundledNativeModules.json`. Verificar com evidência: (a) texto de um builder real rasterizado no Android com `fontMgr` (fidelidade das labels); (b) PNG de uma string real de board via `ImageSVG` + snapshot + `encodeToBytes`, auditando incompatibilidades (estilos CSS → atributos; `rgba()` → opacidade; `font-family` com fallback → fonte única carregada; `<image>`/data-URI; nada de SVG aninhado); (c) caminho do PNG no web (mesmo caminho Skia/CanvasKit ou rasterização nativa do browser — o spike decide); (d) `Text` vs `Paragraph` para labels em tela; (e) teto 4096 no device. Saída: nota go/no-go com os APIs exatos. Sem essa nota, as fases seguintes não começam.
- **Fase 1 — Fundação.** Dependência pinada; mocks Jest para os componentes Skia; checagem de boot CanvasKit no `expo export -p web`; util de fontes + `SkiaEdgeCanvas` compartilhado; avisos de copyright MIT/BSD; typecheck + lint verdes.
- **Fase 2a–2e — Port por canvas** (ordem de risco crescente: LocationGraph → CharacterRelationGraph → StoryGraph → Board → LocationMap). Cada unidade: troca a camada, valida no device (abre, pinch, arrows, labels) e confere paridade web.
- **Fase 3a — Setting `exportFormat`.** Coluna + migração (caminho da migração mais recente) + store + linha em AppSettings (`SingleSelectPill`) + i18n en/pt.
- **Fase 3b — Pipeline PNG.** Rasterização da string do builder com teto de resolução; ajustes de compatibilidade nos builders encontrados no spike (sem mudar a semântica do SVG); os 10 pontos de export passam a respeitar o setting com filename/MIME por formato.
- **Fase 4 — Testes e docs.** Reescrever os testes invalidados do `c31d4cfa` para a camada Skia (+ testes do setting e do pipeline PNG); atualizar comentários de orçamento de bitmap (`spatialCanvas.ts`, `CanvasLine.tsx`); anotar `docs/TESTING_ROADMAP.md`; suite completa + typecheck + lint.

## Risks / Rollback

- **Incompatibilidade builder→Skia-SVG** (CSS, `rgba()`, fallbacks de fonte): mitigado pela auditoria do spike; fallback degradado é PNG de viewport via snapshot de view nativa (API documentada), mantendo SVG integral.
- **Limites de textura/GPU no PNG full-doc**: mitigado pelo teto 4096 + confirmação no device.
- **Bundle/APK maior** (lib nativa): medido na Fase 1 via build; sem ação além de registrar.
- **Churn de testes**: isolado na Fase 4; os testes do `c31d4cfa` são reescritos, não remendados.
- **Rollback**: revert por canvas (unidades independentes); a migração do setting é aditiva (coluna com default), segura para downgrade; nenhum dado de usuário é migrado.

- Verificado aqui: bateria de 17 suites / 173 testes das áreas tocadas, typecheck (só os 2

  `expo export`, render real no Android/web.
- Pendente no device (usuário): abrir as 6 telas no Android em zoom mínimo; nitidez das
  arestas no pinch; labels dos grafos; export SVG inalterado; export PNG nas 10 telas
  (Android + web); persistência do setting; board com imagens (clip-path no raster).
- Follow-up (tela preta no mapa, Android): investigação eliminou composição (o `Canvas`
  Skia é `TextureView` transparente, `setOpaque(false)`, pintado abaixo do plano), culling
  (diff só em comentário) e transform do plano (hook só ganhou o shared value aditivo).
  Sem `ErrorBoundary` no app, qualquer throw no overlay (módulo nativo ausente após update
  só-JS, `matchFont` sem família no Android, reconciler) apaga a tela inteira. Mitigação:
  `SkiaOverlayErrorBoundary` (novo, com teste próprio) embrulhando o overlay nos 5
  canvas — falha Skia agora apaga só as arestas e loga alto (`[SkiaEdgeCanvas:<tela>]`)
  no logcat/Metro. Testes de paint-order atualizados para atravessar o boundary (ordem e
  posicionamento inalterados). Causa raiz ainda aberta: aguardando do usuário (1) se o
  app nativo foi rebuildado após o install, (2) se as outras 4 telas-canvas também
  escurecem, (3) se a web continua OK pós-port, (4) logcat da abertura do mapa.
- Causa raiz da web encontrada: `JsiSkFontMgr.matchFamilyStyle` na web é
  `throwNotImplementedOnRNWeb` — `matchFont` SEMPRE joga na web, e 3 canvas o chamavam
  no corpo do componente (fora do boundary) = tela preta. Fix: `matchEdgeFont` total
  (try/catch → `SkFont | null`, warn único) + labels renderizam só com fonte (4 canvas);
  sem fonte = arestas sem labels, nunca tela preta. Testes: unit do helper + 1 teste de
  integração por canvas (font throw → 0 SkiaText, arestas presentes). Suites afetadas:
  8/8, 42/42; typecheck só com os 2 pré-existentes; eslint 0. Labels na web ficam
  ocultos até um follow-up opcional (fonte .ttf bundlada + `useFont`, único caminho que
  funciona na web). Android nativo ainda pendente das respostas (1)/(2)/(4) acima.
- Causa raiz das arestas ausentes na web: nada carregava o CanvasKit — `Skia.web.js`
  liga `JsiSkApi(global.CanvasKit)` no import com `CanvasKit === undefined`, então TODA
  chamada Skia jogava `TypeError`, contida pelo boundary/fonte como "sem arestas". E o
  v2.2.12 não exporta `LoadSkiaWeb` no entry (só via deep import). Fix: `useCanvasKitReady`
  com split por plataforma — nativo retorna `true`; web resolve o `.wasm` pelo pipeline
  de assets do Metro (`assetExts` já tinha `wasm` pelo wa-sqlite; exports map do
  canvaskit-wasm permite o subpath) e chama o loader com `locateFile` para a URI do
  asset (sem CDN, sem drift de versão, funciona offline/export). `SkiaEdgeCanvas` e
  `SvgRasterHost` (este crasharia a raiz no export PNG, sem boundary acima) seguram
  render + jobs até o boot. Testes: gating do canvas (null→Canvas) + job pendente no
  raster; 9 suites / 45 testes verdes; eslint 0; typecheck só pré-existentes. Boot real
  do WASM não roda no Jest: validar no browser (arestas após ~segundos na 1ª tela,
  `canvaskit.wasm` 200 no network, sem `[SkiaEdgeCanvas]` no console).
- "Continua invisível" na web: causa real era o binding stale — `Skia.web.js` avalia
  `JsiSkApi(global.CanvasKit)` no IMPORT (todas as factories fecham sobre o parâmetro),
  então carregar o CanvasKit depois (gating de render) não revive o objeto `Skia`;
  tudo seguia jogando `TypeError` contido. Fix: entry próprio (`apps/client/index.js`,
  `main` apontado para ele) que na web aguarda o CanvasKit ANTES de requerer
  `expo-router/entry` (falha/stall de 30s bota degradado, sem travar no splash);
  nativo requer direto, idêntico a antes. `ensureCanvasKit` unificado em
  `canvasKitBoot(.web).ts` (entry + hook usam o mesmo); `promiseWithTimeout` novo com
  teste. Prova local: `bun run build` OK, `canvaskit.*.wasm` (8MB) emitido em dist, e a
  string do entry presente no bundle (entry confirmado). Labels seguem ocultos na web
  (`matchFamilyStyle` não implementado — follow-up de fonte bundlada, separado).
- `Image.resolveAssetSource is not a function` na web: react-native-web não implementa
  o static. Troca para `expo-asset` (`Asset.loadAsync`, instalado 12.0.13 + plugin no
  app.json; resolver próprio via registry, `localUri === uri` na web) — mesmo padrão do
  expo-sqlite nesta stack. Re-export OK com wasm emitido. Typecheck/eslint limpos.
- Labels restaurados: `useEdgeFont` com split — nativo usa a fonte do sistema de forma
  síncrona (idêntico ao pré-port em família/pesos/cobertura); web carrega Roboto
  bundlado (`assets/fonts`, Regular 400 + Medium 500 para o 600 do board) via URI do
  `expo-asset` passada como string ao `useFont` (bypassa o `resolveAsset` web da lib,
  que monta URIs sem hash). Geometria/tamanhos/cores/halos inalterados — só a origem
  da fonte mudou. Roboto Apache-2.0 com licença no diretório; subset latin verificado
  por cmap (Latin-1 completo: PT/EN/ES/FR/DE; scripts exóticos viram tofu SÓ na web —
  nativo mantém cobertura total do sistema). Testes: hook web (Medium/Regular/falha);
  11 suites / 51 testes; export emite os 2 TTFs + wasm.
- Labels crashavam tudo na web: `measureText` é `throwNotImplementedOnRNWeb`, o throw
  no render apagava o overlay inteiro via boundary (incluindo o preview do connect
  mode — o "não acompanha o mouse" era arrastar no escuro; mesma causa raiz). Fix:
  `measureEdgeLabelWidth` soma `getGlyphWidths(getGlyphIDs())`, ligado nos dois lados
  (C++ `JsiSkFont` + web `JsiSkFont`; desvia ainda do `accumulate` int do
  `getTextWidth` nativo, que trunca por glyph), com estimativa por-caractere como
  último recurso para medição nunca mais matar arestas. Mock trocado para os métodos
  de glyph (6un); zero `measureText` em src. 12 suites / 53 testes; eslint/typecheck
  limpos (2 pré-existentes).
- Imagens do mapa mortas na web: a view web do Skia descarta o prop `pointerEvents`,
  então o overlay (acima das imagens, abaixo dos nós) engolia todos os gestos das
  imagens — nós seguiam vivos por estarem acima. Fix: `SkiaEdgeCanvas` e o host de
  raster embrulham o canvas numa `View` absoluteFill com `pointerEvents="none"`
  (geometria idêntica, atravessa toque nas duas plataformas). Testes do escudo nos
  dois arquivos. 12 suites / 55 testes; eslint/typecheck limpos.
